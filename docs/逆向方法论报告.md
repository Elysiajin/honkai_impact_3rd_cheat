# 崩坏3 IL2CPP 加密元数据破解方法论

> 本文记录 2026-11 这次 SDK 解密的完整思路：从“名字都解不出来”到类/字段/方法/类型/参数/运行时地址全部可用。
> 重点不是某一组常量，而是**遇到同类加密游戏时如何系统性地找答案**。

---

## 1. 目标与起点

目标不是“能 CE 搜到血量”，而是拿到可编程的 SDK：

1. 类名、namespace、父类、字段名、方法名、返回类型、参数类型；
2. token、flags、RVA/VA；
3. 实体列表、相机矩阵、坐标、伤害/死亡入口；
4. 能稳定重生成（游戏更新后可复现）。

起点只有：`UserAssembly.dll`（约 300 MB，含 255 MB il2cpp 代码段）、`global-metadata.dat`（71 MB）、
一份登录界面的 CE 内存 dump。已知 `global-metadata.dat` 头部被整体加密，类名等字段也二次加密。

---

## 2. 总体策略：把“解密”拆成四层

不要一上来就硬啃算法。按可验证性从高到低分层：

| 层 | 问题 | 主要手段 | 验证物 |
|---|---|---|---|
| L1 结构 | 表在哪、步长多少 | 运行时结构、代码 xref、统计扫描 | token 连续、计数合理 |
| L2 编码 | 每个字段怎么变换 | 反汇编访问函数、常量提取 | 已知样本（Object/String/Locale） |
| L3 语义 | 这个数字代表什么 | 交叉引用 type/field/method 表 | 名字与 token 对得上 |
| L4 运行时 | 怎么调用/怎么拿对象 | 全局链、module methodPointers、invoker | 实机 dump 复现 |

核心原则：**每一层都必须有一个“可证伪的预测”**。
例如解出字段名后，预测“Object 的字段应叫 m_CachedPtr/…”，对不上就说明假设错了，不能继续往下堆。

---

## 3. L1：先找表，不碰加密

### 3.1 利用引擎自己当“说明书”

IL2CPP 运行时必须知道每张表在哪，所以内存里一定有：

- `Il2CppMetadataRegistration`（全局指针，本 build 在 `UA+0x2555498`）；
- 类数组、方法数组、FieldInfo 数组；
- `Il2CppClass` 结构（`+0x20` 名字、`+0x50` 字段数组、`+0x80` 方法数组、`+0xca` 方法数）。

做法：先在运行时 dump 里找到这些结构（类数组、`Object` 的 klass、`FieldInfo`），
用它们反推“元数据里应该有什么”，而不是从文件头猜。

### 3.2 用代码 xref 定位表基址与步长

关键技巧：**不要找常量，找“谁在用这张表”**。

例如方法表：在 `.text` 里搜 `imul reg, idx, 0x1E`（步长 30），找到函数后往前看：

```
mov rdx, [global 0x2555498]   ; registration
mov eax, dword [header + 0xD4]
xor eax, 0x2360832F           ; 表基址解码
add rax, body
lea rax, [rax + idx*0x1E]
```

一次就同时得到：header 偏移、异或常量、正文基址、步长。
同样的方法得到：

```
TYPE  header[0x1C] ^ 0x3AC76B0F  stride 0x52
FIELD header[0x128] + 0xCA7D051D stride 0x0C
METH  header[0xD4] ^ 0x2360832F  stride 0x1E
```

**经验**：自定义 IL2CPP 通常只改头部偏移和 XOR/ADD 常量，不改步长语义。
步长可以通过“token 连续 +1”统计扫描验证：token 字段每行加 1 就是表；加 1 的间隔就是步长。

### 3.3 头部字段识别

`global-metadata.dat` 头部 0x200 字节全是密文。不要逐个猜，按“谁读它”归类：

- 读 `header[off]` 后接 `xor imm32` 或 `add imm32`，再 `add body` → 表基址；
- 读 `header[off]` 后接 `movzx` 再乘步长 → 计数/索引；
- 同一 offset 在多个函数出现 → 重要表。

最后得到一张“header offset → 用途 → 解码常量”的表，写进脚本常量区。

---

## 4. L2：字段级编码怎么破

### 4.1 名字不是简单 XOR

以方法名为例，反汇编 `Method::GetName`（本 build `0x6298A0`）：

```
hash = MKEY(index)
nameIndex = ((raw + 0xB509F32B) & 0xFFFFFFFF) ^ hash
```

`MKEY` 是一串乘/异或/移位：

```
MKEY(i) = ((((i*0xDB9B) ^ 0x1A58D018) * 0x1339AE8B ^ 0x1FFFA93E)
           * 0x27F47E6A + 0xBF9490F71BB2A5A) >> 0x14
```

得到公式后**先验证再使用**：抽 2,000 个方法，名字索引必须能解成合法标识符；
再拿 `Object.Equals`、`Locale.GetText` 这种已知方法对照。

### 4.2 同类字段往往共用一套模板

- 类表：name/namespace/parent/flags/token 全部同一 `TKEY`；
- 字段表：`K0=FKEY(fieldIndex)`，`K1=K0^0x6C0D9DD8`；
- 方法表：`MKEY(globalMethodIndex)`。

**经验**：不要为每张表重新发明算法。先假设“同一家族同一 key”，用已知样本反推常量，
再验证其它字段；只有验证失败才换 key。

### 4.3 字符串是最后才碰的

字符串索引 = `(len<<24)|src`，数据在正文 `+0x1EB360`，每 8 字节：

```
raw ^= (src*KS_SRC + KS_ADD) ^ KS_XOR + j*SD
```

字符串解出来后，才能验证类名/方法名/参数名，所以它必须早于 L3，但不必早于 L1。

---

## 5. L3：类型系统——这次最关键的突破

### 5.1 问题

字段定义表里的 `typeIndex`（如 `0x44146`）不是 `byvalTypeIndex`（如 `0x427`），
一开始只能解出返回类型，字段全是 `object /*type 0x...*/`。

### 5.2 思路：从运行时 FieldInfo 的指针反推类型表

`FieldInfo+0` 存的是**编码后的 `Il2CppType*`**。在 CE dump 里读 `List<T>._items` 的 FieldInfo：

```
encoded = 0x7ffd8cc03380 + 0x527998825445eff7
decoded = 0x7ffd8cc03380
```

`decoded` 落在 `.rdata`，用文件基址换算成 RVA。再用方法表里 typeIndex=0x45506 的公式反推：

```
typesBase = decoded - 0x45506 * 0x10 = UA + 0x78E320
```

### 5.3 验证

在 `0x78E320` 读 16 字节 `{data, bits}`：

- `bits>>16 & 0xFF` 是 type enum；
- 0x08=I4、0x0C=R4、0x0E=STRING、0x12=CLASS、0x1D=SZARRAY…

用它解 `SmallXmlParser` 的 12 个字段，得到
`StringBuilder / TextReader / Stack / char[] / string / int / bool`，与 Mono 源码完全一致。
再解 `Camera.onPreCull=CameraCallback`、`Vector3.x/y/z=float`，确认无误。

**方法论**：运行时结构是“已知答案的一半”。
`FieldInfo.type` 本身就是指针，顺着它做指针算术，比从文件里盲扫 16 字节结构可靠得多。

## 6. L3.5：参数表消失后的替代路径

### 6.1 先证明它真的不在

方法记录 0x1E 字节的真实字段全部解出后确认：**没有 parameterStart/parameterCount**。
对 71 MB 做两轮扫描（名字索引结构过滤 + TypeIndex 结构过滤）也没找到 ParameterDefinition 表。
结论：本 build 把参数定义裁掉了。

### 6.2 用 invoker thunk 反推签名

每个唯一签名都有运行时 invoker：

```
invoker(MethodInfo* rcx, void* this rdx, void** args r8, void* ret r9)
mov rcx, [r9]        ; 第 0 个参数的指针
mov edx, dword [rcx] ; int
movss xmm1, [rcx]    ; float
```

扫描 `[r9+disp]` 的加载 + 解引用宽度，得到参数类型。
能解出 137,182 个运行时方法（其中 53,891 个有参数），例：

```
Camera.set_fov(float)
Object.Equals(object)
Object.Equals(object, object)  static
String.Substring(int)
```

**方法论**：当元数据被裁剪，**生成代码就是新的元数据**。
invoker/prologue/调用点都能恢复签名，代价是精度有限（object vs string 分不出来）。

## 7. L4：运行时地址——module methodPointers

### 7.1 问题

登录界面 dump 里 `Transform/Time/AvatarManager` 的 MethodInfo 数组是空的，
因为类还没初始化；但代码一定存在。

### 7.2 解法

IL2CPP 每个 module 有 `methodPointers[]`，按 **token RID-1** 索引：

1. 从 `.data` 找数组基址（用已知 `MonoMainCamera` 方法 RVA 反推）；
2. 本 build module 211 数组基址 = RVA `0x1F6C070`；
3. `rva = methodPointers[ (token & 0xFFFFFF) - 1 ]`。

验证：`MonoMainCamera.CameraForwardLerp` token `0x0600B7B4` → 数组槽位正好落在
`0x1C6E08`，值与已知 RVA 对上；`get_AvatarManager`、`GetAllAvatars` 也逐一核对。

**方法论**：token 是元数据和代码之间的稳定纽带。RID 是每 module 连续的，找到数组基址后，
所有未实例化方法的 RVA 都能离线算出来。

## 8. L4：战斗对象与函数入口

### 8.1 管理器链

反汇编 `get_AvatarManager`（`0x43BE010`）得到全局链：

```
*(UA+0x2641588) = MethodInfo*
MethodInfo+8   = klass
klass+0x18     = ?
+0x18 -> +0x10 -> +0x30 -> [E] = AvatarManager
```

`get_MonsterManager`（`0xA0AE480`）同链，`*(UA+0x2642EA8)`。

### 8.2 用战斗 dump 验证

进入关卡后重新 dump，实测：

- AvatarManager `0x7001dddaf20`，`+0x50` List，size=3：MonoFukaNL/MonoFuka/MonoSakuraYS_BattleY
- MonsterManager `0x7001d08f540`，`+0x18` List，size=3：Mono_DG_030/020_BattleY
- List 布局：`+0x10` items、`+0x18` size、数组 `+0x20` 元素
- 怪物坐标 `+0x734`（从 `get_LastValidPosition` 的汇编直接读出）

### 8.3 相机与战斗

- `Camera.get_main`、`get_worldToCameraMatrix`、`get_projectionMatrix`、`pixelWidth/Height`
- `VP = P * V`，列主序；`sx=(ndc.x*0.5+0.5)*W`，`sy=(0.5-ndc.y*0.5)*H`
- `DieNow(bool)` 秒杀；`BaseMonoAvatar.BeHit` 12 字节 patch 实现无敌

**方法论**：先读字段（不执行代码）把对象图确认，再调函数。
`get_LastValidPosition` 这类 getter 的汇编通常只有几条，直接读出字段偏移，比调用安全。

## 9. 对加密游戏的可复用打法（Playbook）

### 9.1 静态阶段

1. 识别引擎：Unity/IL2CPP 版本、`global-metadata.dat` 魔数/头部是否正常；
2. 看节区：il2cpp code 段、`.data` 里的注册结构、`.rdata` 里的静态 `Il2CppType`；
3. 找导出（常常被抹掉），找字符串（即使字符串加密，也会残留格式串）；
4. 不要先写解密器，先写“把内存 dump 成文件”的工具。

### 9.2 找结构

1. 运行时扫描 `Il2CppClass`：`+0x20` 名字、`+0x50` 字段、`+0x80` 方法；
2. 找 `Il2CppMetadataRegistration`：它一定被全局指针引用，`+0x70` 附近常是 types；
3. 用已知类（`Object`、`String`、`Locale`）做锚点，反推表基址/步长；
4. token 连续性是免费的结构探针：加 1 → 表；间隔固定 → 步长。

### 9.3 找编码

1. 反汇编“读这个字段的函数”，不要猜算法；
2. 常量通常以 `xor imm32` / `add imm32` / `imul` 出现；
3. 先解名字，再解类型，再解参数；
4. 每步都拿已知样本验证，错误就回退假设，不要叠加未验证的假设。

### 9.4 元数据被裁剪时

| 缺什么 | 从哪里拿 |
|---|---|
| 字段偏移 | 字段 getter/setter 的汇编、对象内存差分 |
| 参数类型/数量 | invoker thunk、方法 prologue、调用点 |
| 未实例化方法 RVA | module methodPointers + token RID |
| 静态字段 | 类静态区 + 字段名/类型交叉验证 |
| 对象列表 | 管理器 getter 的全局链 + List 布局 |

### 9.5 工程化

- 所有常量写进一个 `build.json`/脚本顶部，标注版本；
- 生成器幂等：`sdkgen.py --dump` 一条命令重生成；
- 每次游戏更新：先 diff 头部常量/步长，再跑已知样本（Object/SmallXmlParser/String）；
- 覆盖层只读优先；必须调用托管函数时，先确认线程归属，再做最小 hook；
- 崩溃时先看“链路哪一跳为空”，不要把问题归咎于加密。

## 10. 本次独立完成的部分与边界

**独立完成**：
- 方法表 0x1E 的真实字段布局与 token/decl/name 公式；
- 静态 `Il2CppType` 表定位（`0x78E320`）与全部字段/返回类型解析；
- 参数缺失的证明与 invoker 反推方案；
- module methodPointers 定位与未实例化方法 RVA 恢复；
- 管理器链、List 布局、怪物坐标、相机矩阵、DieNow/BeHit 的运行时验证；
- 覆盖层 ESP / 秒杀 / 无敌的落地。

**边界**：
- 字段偏移（FieldInfo 无 offset，需按布局或 getter 汇编补）；
- 参数名（元数据被裁）；
- 泛型实例化名字、静态字段 VA；
- 所有 RVA/全局偏移仅对当前 build 有效，更新需按第 9 节重跑。

---

## 11. 结语

加密 IL2CPP 的破解不是“找到某个 KEY”，而是建立一条**可验证的证据链**：

> 运行时结构 → 表位置 → 字段编码 → 语义映射 → 代码/对象入口 → 实机复现

只要每一环都有独立验证物，即使元数据被改得面目全非，也能一步步还原出可编程的 SDK。
这套流程同样适用于其它 Unity 游戏：先找引擎自己的结构，再让代码告诉你常量，最后用真机 dump 做最终裁判。
